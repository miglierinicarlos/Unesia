# ADR-001: IPC Mechanism — BSD Sockets over RPC Frameworks

| Field | Value |
|-------|-------|
| **Date** | Week 1 |
| **Status** | Accepted |
| **Lab** | v0.1 |
| **Deciders** | All squads + Instructor |

## Context

The EOP platform requires inter-process communication between distributed services. Multiple options exist at different abstraction levels: raw BSD/POSIX sockets, gRPC over HTTP/2, ZeroMQ, or message brokers such as RabbitMQ. The choice at this layer determines the degree of control engineers have over the communication model, and directly affects the learning objectives of v0.1.

The core engineering objective of v0.1 is for engineers to operate at the transport layer — managing file descriptors, implementing message framing, handling partial reads and writes, and reasoning about concurrency over network connections.

## Decision

The C++ server uses BSD/POSIX sockets directly. The server calls `socket()`, `bind()`, `listen()`, `accept()`, `recv()`, and `send()` without any intermediate RPC or messaging library. The C client library uses the same POSIX socket API.

The message protocol (types, framing, serialization) is designed by the squad and documented in ADR-003.

## Alternatives Considered

| Alternative | Reason Rejected |
|-------------|----------------|
| gRPC / Protobuf | Abstracts the socket entirely. Engineers would work at the RPC layer without understanding the transport mechanics underneath. |
| ZeroMQ | Still abstracts framing and connection management. Same objection as gRPC for v0.1 context. |
| RabbitMQ / Kafka | Introduces a broker dependency and shifts the problem domain entirely. Not appropriate for distributed systems foundations. |
| Unix Domain Sockets | Limited to a single host. EOP requires inter-node communication across the network from the start. |

## Consequences

**Positive:**
- Engineers develop direct competency with the POSIX socket API used in production systems (databases, web servers, game engines)
- Full control over framing, concurrency model, and error handling — these become explicit engineering decisions
- The protocol designed in v0.1 is owned by the squad and documented in ADRs, not generated by a framework

**Negative:**
- More implementation effort compared to using gRPC. Framing, partial read handling, and concurrency must be implemented from scratch
- Protocol evolution requires discipline: backward compatibility is not enforced by a compiler — it is enforced by the ADR-003 versioning policy

**Constraints Introduced:**
- All message framing must handle partial `recv()` returns. The protocol must define message boundaries unambiguously
- Resource management (file descriptors, buffers) falls entirely on the application. RAII is mandatory per NFR-3
- The concurrency model for handling multiple clients must be explicitly chosen and documented in ADR-002
